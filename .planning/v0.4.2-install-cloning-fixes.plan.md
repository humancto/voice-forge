# v0.4.2 — install-cloning robustness + MPS default on Apple Silicon

Two real install-cloning bugs surfaced during a live v1→v2 engine upgrade on this machine. Both prevent the upgrade from succeeding on any user who is migrating rather than installing fresh.

PLUS a **3× synth speedup on Apple Silicon** by defaulting `VOICEFORGE_FISH_SYNTH_DEVICE` to `mps` when torch's MPS backend is available. Same fish-speech S2 Pro model, same studio-quality voice clone (whisper-verified character-perfect on the Tyson clone), measured at ~8 min total vs 17 min CPU baseline for the same paragraph.

## Bug 0 (NEW) — CPU is the default on Apple Silicon when MPS works fine

**Symptom.** `voiceforge note` on M-series CPU runs at ~1/62× realtime (1018s synth for 16.4s audio). The hook for `mps` was already plumbed in `scripts/fish_speech_synth.py:240` (`device = os.environ.get("VOICEFORGE_FISH_SYNTH_DEVICE", "cpu")`) but defaulted to CPU. Same script with `VOICEFORGE_FISH_SYNTH_DEVICE=mps` on the same M2 ran the same paragraph at ~1/21× realtime (~360s pure synth) — **~3× faster, same model, same checkpoints, same studio quality** (whisper-perfect transcription of the cloned Tyson voice).

**Fix.** Replace the hardcoded `"cpu"` default with a `_detect_default_device()` helper:

```python
def _detect_default_device() -> str:
    try:
        import torch
        if torch.backends.mps.is_available() and torch.backends.mps.is_built():
            return "mps"
        if torch.cuda.is_available():
            return "cuda"
    except Exception:
        pass
    return "cpu"

device = os.environ.get("VOICEFORGE_FISH_SYNTH_DEVICE", _detect_default_device())
```

User can still force CPU via `VOICEFORGE_FISH_SYNTH_DEVICE=cpu` (e.g. for memory-constrained Macs or debugging). Net effect: every M-series Mac that does `voiceforge note` after v0.4.2 gets the ~3× speedup automatically with no config changes.

**Risk:** MPS has higher memory pressure than CPU. On a 16 GB Mac, the 10 GB fish-speech S2 Pro checkpoints + MPS scratch may swap. Mitigation already in script: `set_default_device()` falls back to CPU on init failure. Caveat documented in install-cloning output.

## Bug 1 — `--force` mode leaves `$REPO_DIR` in place

**Symptom.** A user on a v0.3 / v0.4-pre-fish install has `~/.voiceforge/cloning/repo/` populated with the legacy GPT-SoVITS clone (origin = `github.com/RVC-Boss/GPT-SoVITS`). Running `voiceforge install-cloning --force` to upgrade to fish-speech S2 Pro: the script's "fresh start" branch removes `$VENV_DIR` + `$MARKER_FILE` but NOT `$REPO_DIR`. Later in the script:

```bash
if [[ ! -d "$REPO_DIR/.git" ]]; then
  step "cloning fish-speech @ $FISH_SPEECH_SHA"
  run retry 3 5 git clone --quiet "$FISH_SPEECH_REPO" "$REPO_DIR"
fi
```

The directory exists (with GPT-SoVITS contents); the `if` is false; the fresh clone is skipped. The next step asks `origin` (which still points at the GPT-SoVITS remote) for a fish-speech SHA — fails with "not our ref."

**Fix.** `scripts/install_cloning_fish.sh` line 258 (`force)` branch) `rm -rf` also includes `"$REPO_DIR"`. Mirror the same logic on line 145 (`uninstall`) which already does this.

## Bug 2 — `git fetch origin <SHA>` doesn't work on GitHub's wire protocol

**Symptom.** Even on a fresh `repo/` (post-fix-1), the script's "checking out pinned SHA" step does:

```bash
run git -C "$REPO_DIR" fetch --quiet origin "$FISH_SPEECH_SHA"
run git -C "$REPO_DIR" reset --quiet --hard "$FISH_SPEECH_SHA"
```

GitHub's `upload-pack` only serves refs (branches, tags), not arbitrary SHAs. The error is `fatal: remote error: upload-pack: not our ref <hex>` even though the SHA IS reachable from `main`. Verified manually: a vanilla `git clone <repo>` brings the SHA in the local object database; only the explicit `fetch origin <SHA>` step fails.

The fetch step exists to refresh stale clones on subsequent invocations. It can be replaced with `fetch origin main` (the upstream default branch) — that's a ref, GitHub serves it, and any SHA reachable from `main` becomes locally available for the subsequent `reset --hard`.

**Fix.** `scripts/install_cloning_fish.sh` line 293: replace `git fetch --quiet origin "$FISH_SPEECH_SHA"` with `git fetch --quiet origin main`. The `git reset --hard "$FISH_SPEECH_SHA"` on line 296 is unchanged and handles the actual checkout.

**Risk note.** If upstream ever drops a SHA we depend on (squashes it out of main's history), the reset will fail loud with a clear "unknown revision" error. That's a deliberate signal that the pin needs bumping — not a silent breakage.

## Risk

Both fixes are tiny and surgical. Bug 1's fix is additive (only removes a directory that the alternative already handles correctly in the `uninstall` branch). Bug 2's fix narrows what we ask of the network (a `main` fetch is strictly less restrictive than a SHA fetch on GitHub's protocol). No new behavior, no new dependencies, no schema changes.

Pin staleness — if upstream's `main` ever moves backward past our pinned SHA, the reset will fail loud. Today's pin (`3dd1f85c...`, dated 2026-04-06) is currently reachable from `main` (`02995ed7...`). Future bumps need to verify reachability before landing.

## Out of scope

- Bumping the pinned fish-speech SHA. Today's pin still works; the network-protocol fix unblocks it.
- Switching the install script to a tarball-based fetch (avoids the git-protocol question entirely but adds a sha256-pin step). Worth considering for v0.5 but not for the smallest viable fix.
- Pre-flight `git remote -v` check that the existing `repo/` actually points at the expected upstream (would catch a future regression where a user manually swapped origins). Lower-priority safety net; can ship in v0.4.3.
